# Life Context — Agent Memory 与 Data Infrastructure

更新：2026-10-11。状态：研究问题草案；尚无实验结果或新颖性结论。

## 两个观察角度

Agent memory 关注 agent 应该记住什么、怎样帮助后续任务。Data Infrastructure 关注数据如何进入系统、被转化、更新、组织，并可靠地交给不同消费者。

本项目的数据链路：多来源记录 → 候选认识提取 → 用户确认 → 当前状态维护 → 任务上下文生成 → 不同 agent 消费。

聊天记录、自述和后续可能加入的问卷是输入；目标、约束和偏好是派生数据；核心文件是任务视图。个人记忆提供应用场景，数据派生、更新与消费提供基础设施切口。

采用 SQLite、MCP、权限或版本管理，只能说明存在工程需求；它们本身不证明研究贡献。产品可以使用成熟方案，研究独立评估残余问题。

## 核心文件的消费契约（设计建议）

核心文件是从当前已确认状态及其来源中，为特定任务生成、具有版本和权限范围的上下文视图。

应明确：任务/项目范围、允许访问的来源与敏感度、内容预算及单位、状态版本、生成时间、所引用条目与来源、过期或缺失提示。读取凭据证明系统交付的版本，不能证明模型理解或遵循。

MCP 提供资源与工具的接入机制；一致性、来源含义和维护策略需要系统自己定义。Markdown 快照提供兼容回退，必须标明版本并规定刷新方式。

## 运行示例

用户先确认“本月副项目每周最多六小时”，之后改为三小时。系统需要识别新旧来源与正式约束，找到受影响的任务上下文，处理旧版本 agent 的更新，并提醒复核可能受影响的旧建议。

区分三种影响：

- 确定更新：正式时间预算及直接引用它的视图。
- 可能需复核：根据原预算生成的可行性分析。
- 暂无证据受影响：其他无关偏好或项目事实。

自然语言语义依赖可能不完整。不能把所有关联都作为确定依赖，也不能仅因没有显式边而宣称不受影响。用户撤回来源、来源内容修订和用户修正认识分别建模，具体规则待设计。

## 候选研究问题

来源持续变化时，如何以较低维护成本，让多个任务上下文保持足够新鲜，并正确标记需要复核的内容？

假设：在真实反复访问、局部更新的负载下，来源与依赖感知的选择性维护，可以在相同正确性与时效要求下，降低重建与人工复核的总成本。

该假设尚未验证。负载可能很小，简单按需重建已经足够；语义依赖识别也可能比完整重建更昂贵。应先测真实损失，再决定是否需要研究机制。

## 最小证伪方案

- 输入：经用户授权的真实使用轨迹，或明确标为合成的来源变化/读取轨迹。记录新增、修订、撤回、确认及任务请求。合成压力检查与真实收益分开报告。
- 隔离变量：先使用已确认条目与明确依赖，或固定提取器、模型、提示及版本；分别测提取错误与维护错误。不能把模型质量提升算成维护收益。
- Baseline：每次请求完整重建；按来源版本检查并按需重建；显式依赖下的选择性更新。给予相同权限、预算、允许的缓存和正确性要求。
- 参考结果：以受控完整重建结果和预先标注的影响集检查视图一致性。可能影响的语义判断单独标注，保留未知类别。
- 划分：按用户/项目分组；策略调参与阈值选择使用探索集，冻结后再评估保留轨迹。单人结果不宣称跨用户泛化。
- 主指标：满足预设正确性与时效约束下的端到端维护成本。工程耗时、模型调用、读取/写入量与人工分钟分别报告，未预设权重时不合成单一分数。
- 辅助指标：过期条目漏报、影响标记误报/漏报、请求延迟、CPU/RSS、核心文件体积、增量维护开销。任何零错误结论仅限已检查样本。
- 成功 Gate：相对最强简单 baseline，在保留轨迹中存在预先定义的、有实际意义的净收益；计入依赖构建、索引、更新、重新生成和人工确认成本，且满足相同正确性要求。数值阈值待探索测量后冻结。
- 停止条件：按需重建已经足够；收益只出现在人为重复或特殊微基准；依赖误判造成错误传播；维护/确认成本抵消收益；收益依赖放宽权限、正确性或时效要求。
- 当前结论：未验证假设，可作为工作负载观察方向；不能据此声称论文贡献。

## 产品验证与科研验证分开

产品验证回答用户是否愿意持续使用、净节省时间和迁移是否可靠。研究验证回答强 baseline 后是否有可泛化的残余损失，以及新机制能否解释并降低该损失。小规模个人试用提供探索性线索。

问卷画像主要增加输入与分析方式；它不自动增强基础设施研究贡献。标准化量表的分数解释另需效度、信度与适用人群证据，自制引导问卷不继承这些属性。
